# CTRL 26 数据绑定机制：皮肤如何读取游戏数据

本文档说明 CTRL 26 皮肤（以及任何 FM26 皮肤）与游戏数据之间的关系：皮肤能拿到哪些数据、通过什么机制拿到、以及这些声明在文件中的结构格式。配合 [项目说明.md](./项目说明.md) 食用，那份文档讲"每个目录是干什么的"，本文讲"数据是怎么流的"。

---

## 1. 核心结论：皮肤是纯声明式的，没有"读数据"的代码

FM26 皮肤**不包含任何可执行逻辑**——没有插件 API、不能访问存档数据库、不能跑脚本、不能写回游戏数据。皮肤与游戏数据的唯一交互方式是 Unity UI Toolkit 之上的 **SI.Bindable 数据绑定框架**：

```
游戏引擎（数据源）
   │  运行时求值绑定路径，把值"推"给 UI 元素
   ▼
皮肤（声明侧）：UXML 里写 binding="kind=1; path=match.MatchScore"
                → 引擎把比分填进这个元素
```

- 皮肤**声明**"这个文本框显示 `match.MatchScore`"，求值和刷新全部由引擎完成。
- 因此**皮肤能"读"到什么 = 游戏 bundle 里暴露了哪些绑定路径**，全集由游戏版本决定。
- USS（样式表）完全不接触数据；它只能通过 UXML 绑定切换类名（`style-class-on-visible`）来间接"响应"数据变化。

想找新数据源，不是查 API 文档，而是**去游戏原版资产的序列化转储里挖现成的 `m_path`**（见第 9 节），或者查 26.3 逆向得到的**属性注册表全量清单**（7805 项，`F:\fm-research\registry_parsed.json`，见 8.5 节）——后者才是理论上限。

## 2. 四种数据消费机制总览

| # | 机制 | 所在目录 | 一句话说明 |
| --- | --- | --- | --- |
| 1 | **UXML 绑定路径** | `panels/*.uxml`、`_uabea/*/win|mac/*.json` | 主要机制：`binding="kind=1; path=…"` 声明元素与数据路径的对应 |
| 2 | **表格列 ID** | `table-views/*.json` | 用 `columnID` 引用游戏内置的数据列 |
| 3 | **图标参数化选择器** | `graphics/*/mapping.json` | 引擎按数据谓词（能力/潜力/青年队…）匹配替换贴图 |
| 4 | **磁贴模板引用** | `tile-layouts/*.json` | 按 `guid + path_id` 引用 bundle 内磁贴，数据绑定在磁贴模板内部 |

## 3. 机制一：UXML 数据绑定（主要机制）

### 3.1 文本形式（`panels/` 中直接可见）

绑定写在 `si:` 命名空间的可绑定元素上，本仓库中所有绑定均为 `kind=1`（直接属性绑定）：

```xml
<!-- 值控制可见性 -->
<si:SIVisible binding="kind=1; path=match.IsInOverview" />

<!-- 值变化时切换 USS 类名（USS 间接响应数据的唯一通道） -->
<si:SIVisible binding="kind=1; path=match.MatchHighlightVisibility"
              style-class-to-apply-on-visible="match.MatchHighlightVisibility"
              style-class-on-visible="match.MatchHighlightVisibility" />

<!-- 二分支容器 -->
<si:BindableSwitchElement binding="kind=1; path=match.IsInOverview">
```

常用的可绑定元素/控件（均出现在本项目 UXML 或转储中）：

| 元素 | 作用 |
| --- | --- |
| `si:BindingRoot` | 绑定树根，承载 value-properties |
| `si:BindingSetter` / `si:BindingExpect` | 设置/断言绑定上下文 |
| `si:BindingRemapper` | 上下文重映射（见 3.2） |
| `si:SIVisible` | 按布尔值显隐、切类名 |
| `si:SIText` / `SIImage` / `SIToggle` 等 | 文本 / 图片 / 开关的值绑定 |
| `si:BindableSwitchElement` | 按值二选一显示子树 |
| `si:DynamicItem` | 动态列表项 |
| `si:EventTrigger` / `fm:SIDelayEvent` | 事件与延迟事件 |

辅助属性：`invert-direct-binding`（取反）、`bind-direct-as-mask`、`always-bind-children`（不可见时是否仍刷新子树）。

### 3.2 上下文重映射（BindingRemapper）——同一模板接不同数据

磁贴/组件模板会被多处复用，模板内部只写**局部名**（如 `team`），由外层的 `BindingRemapper` 把局部名重定向到真实数据路径。`_uabea/nav-next_match` 转储中的序列化实例：

```json
"Mappings": {
  "Array": [
    {
      "m_serialisedType": 0,
      "from": "team",
      "to": { "m_path": "human.team.NextMatchOpponent" },
      "type": { "id": 1145176088 }
    }
  ]
}
```

含义：这个"下一场比赛"组件里所有 `team.xxx` 的绑定，实际读的是玩家球队的下一场对手。`from → to` 就是模板复用的接线柱。

### 3.3 序列化形式（`_uabea/` 转储中）

UXML 文本与 UABEA JSON 转储的对应关系（`UABEA-Notes.md` 强制要求的格式）：

```
binding="kind=1; path=X"   ⟷   "m_direct": { "Path": { "m_path": "X" }, "Nullable": 0 }
```

- 两个平台（win/mac）都必须用 `Path + Nullable` 包装，禁止旧的扁平 `"m_direct": {"m_path": …}`。
- 转储里每个可绑定属性带 `*_UxmlAttributeFlags`（是否在 UXML 层显式设置）。
- 结构性改动（增删 `references.RefIds`、`rid`、`uxmlAssetId`、`inlineSheet`）后必须互相校验一致才能回导。

### 3.4 三类特殊路径

1. **Visual Script 路径**：`binding="kind=1; path=d3eeb50ead51b944dbc3777e94fb9af3; is_visualscript=True"`——绑定到游戏内 Visual Scripting 计算图，值由游戏侧脚本算出，皮肤只管显示（例：VAR 提示的显示条件）。
2. **哈希路径**：`0043cf8d52dec664881cdc004dc65dea` 等 32 位十六进制串——混淆后的绑定目标，语义需对照原版资产猜。
3. **面板局部状态**：`selected-tab`、`polygonselected`、`messagefiltervisible` 这类小写路径是 UI 自身的状态，不是游戏数据。

## 5. 机制二：表格列 ID（`table-views/`）

自定义表格不写绑定路径，而是组合游戏内置的列标识符。每列结构：

```json
{ "columnID": "transfer-value", "widthOverride": 120,
  "minWidthOverride": 120, "required": 0, "sortingDisabled": 0 }
```

本皮肤用到的 23 个 columnID：

- **身份**：`portrait-name`、`age`、`club`、`nation`、`second-nationality`、`position`
- **价值与声望**：`transfer-value`、`world-reputation`、`inf`
- **国字号**：`international-caps`、`international-youth-caps`
- **球探**：`knowledge`、`recommendation-grade-only`、`current-ability-stars`、`potential-ability-stars`
- **属性**：`attribute-acceleration`、`-pace`、`-aggression`、`-bravery`、`-determination`、`-jumping-reach`、`-teamwork`、`-work-rate`

列的语义、格式化、排序全部由游戏内置实现，皮肤只决定"选哪些列、多宽、可否排序"。

补充（26.3 调查）：列 ID 是数据驱动而非代码注册（全集 1851 个见 `F:\fm-research\column_ids_union.txt`，含每列完整绑定接线的 tablefactory 转储在 `F:\fm-research\dumps\ui-tablefactories_assets_all.bundle.txt`）。其中有**裸数值能力列**可直接组合：`hidden-current-ability`（绑 `Player.PlayerCurrentAbility`）、`hidden-potential-ability`（绑 `Player.PlayerPotentialAbility`），以及 `ca`、`pa` 等调试列。

## 6. 机制三：图标参数化选择器（`graphics/*/mapping.json`）

图标替换不是路径绑定，而是**数据谓词匹配**。以星级图标为例：

```json
"max-full-youth.png": "ability=max, potential level=fullfilled, youth=true_*"
```

引擎取球员的当前能力（ability）、潜力档位（potential level）、是否青年队（youth）去匹配右侧谓词，`_*` 为通配后缀。也就是说：**换图标 = 按"数据取值组合"提供贴图**，数据本身仍由引擎读取。`condition`、`morale`、`fatigue`、`sharpness` 等文件夹同理。

## 7. 机制四：磁贴模板引用（`tile-layouts/`）

布局 JSON 只声明"放哪个磁贴、放哪"：

```json
{ "tile": "SquadFirstTeamTile_8x8", "x": 0, "y": 0, "w": 8, "h": 10,
  "isDynamic": true, "guid": "cb6226a4…", "path_id": "4009900239504513551" }
```

`guid + path_id` 指向 bundle 内的磁贴 UXML 资产，**该磁贴读什么数据由其内部绑定决定**（多数在游戏原资产里）。想给磁贴换数据源，要么在外层用 BindingRemapper 重映射，要么进 `_uabea` 改磁贴模板内部绑定。

## 8. 能力边界（重要）

| 能做 | 不能做 |
| --- | --- |
| 显示任何已注册绑定路径的值（**含 CA/PA 数值**，见 8.5 节） | 读取未注册属性（注册表之外的名字一律 Invalid） |
| 按值切换可见性/USS 类名 | 执行计算、条件逻辑（visual script 路径是游戏侧已有的图） |
| 组合内置表格列（含 `hidden-current-ability` 等数值列） | 自定义全新列类型 |
| 按数据谓词换贴图 | 写回任何游戏数据 |
| 引用任意内置磁贴模板 | 从零构造读取新数据的磁贴（只能复用/接线） |

## 8.5 CA/PA 可达性（26.3 逆向结论）

**结论：CA/PA 数值可绑定、可显示。** 数据层架构与旧假设不同：

1. **没有 C# 数据类**。UI 数据层是注册表式的：`SI.Bindable.Reference.Core.PropertyRegistration.Initialise` 在启动时把 7805 个属性注册进 `IdentifierSet`（名字 → 4 字节 `PropertyID`，部分 ID 是 ASCII 助记：`PlayerCurrentAbility`=0x50434142="PCAB"）。属性值由 C++ 模拟引擎按 `(ReferenceID, PropertyID)` 计算。
2. **白名单机制**：`binding path` 的属性名经 `IdentifierSet.GetID()` 大小写不敏感哈希查找，未注册的名字一律 Invalid——路径全集 = 注册表 7805 项（已导出 `F:\fm-research\registry_parsed.json`），远大于 UI 资产实际用到的 11014 条 `m_path`（其中 38 个 ability/potential 属性已注册但游戏 UI 未用，如 `PotentialAbilityStars`、`CurrentAbilityScore`，是皮肤的"新"数据源）。
3. **`kind=` 的含义**：`Kind` 枚举 `Value=1 / Reference=2`。值绑定拿数据，引用绑定拿可导航对象。
4. **属性值类型是运行时原生侧决定的**（`*Reference$$GetPropertyTypeInternal` 互操作调用），静态文件查不到；数值性靠游戏用法判定。
5. **`tactic.PlayerContextTacticAbility` 是区间对象不是裸数值**：有 `.MaxValue` 子属性、配套 `TableSortPlayerContextTacticAbility` 排序包装；消费端是 `FMStarRatingTemp`（int 星级刻度 + `MinBinding/MaxBinding` 定标，见 `role.currentabilitystars.minvalue/maxvalue`）。想显示数字 CA 应改用 `Player.PlayerCurrentAbility`。

表格列层面同样有裸数值列可组合：`hidden-current-ability`、`hidden-potential-ability`、`ca`、`pa`（列 ID 全集 1851 个见 `F:\fm-research\column_ids_union.txt`；注意 `current-ability` 列多数工厂里实际绑的是星级区间）。

## 9. 如何挖掘新的绑定路径

1. 用 UABEA 打开游戏原版 bundle（皮肤涉及的六个：`ui-tiles/match/widgets/panelids-uxml/tactics/calendar_assets_all`，以及其他）。
2. 导出目标资产的 JSON 转储，搜索 `"m_path"`。
3. `_uabea/UABEA-Notes.md` 的 **Asset index 表**（bundle + 文件名 + Path ID）是现成的入口清单——那正是皮肤作者挖路径时留下的地图。
4. 在自己的 UXML 里以 `binding="kind=1; path=…"` 引用，或在转储中通过 `m_direct` 包装写入。
5. 结构性改动后按 `UABEA-Notes.md` 校验 `references` / `rid` / `uxmlAssetId` 一致性。

## 10. 最小实战示例

给自定义面板接一个"下一场对手名"：

```xml
<ui:UXML xmlns:ui="UnityEngine.UIElements" xmlns:si="SI.Bindable">
  <si:BindingRoot>
    <si:BindingSetter>
      <!-- 把局部上下文 "team" 接到玩家下一场对手 -->
      <si:BindingRemapper>
        <si:BindingRemapperMappings>
          <si:BindingRemapperMapping from="team" to="human.team.NextMatchOpponent" />
        </si:BindingRemapperMappings>
      </si:BindingRemapper>
      <!-- 在此子树内即可用局部路径绑定 -->
      <si:SIText binding="kind=1; path=team.Name" />
    </si:BindingSetter>
  </si:BindingRoot>
</ui:UXML>
```

（示意写法；实际属性名以游戏内序列化格式为准，可对照 `panels/PortalMessagesTile.uxml` 等现成文件。）

## 11. 实战落地：球员属性界面显示 CA/PA 数值（UABEA 补丁方案）

第 8.5 节结论的第一次应用。**最终落地方式：`_uabea/player-attributes-ca-pa/` 补丁**（详见其 `PLAYER_ATTRIBUTES_CA_PA_CHANGES.md`），在 `ui-tiles_assets_all` 的 `PlayerAttributesLargeBlock` 资产（Path ID `7199728689344018492`）序列化层直接注入一行两列的静态标签 + 数值绑定：


### 第一次尝试（panels/ UXML 路线）为何失败——闪退事后分析

2026-09-13 首次把改动写进 `panels/PlayerAttributesLargeBlock.uxml`（信息列加 CA/PA 行），FM Skin Builder 构建后进属性界面闪退：

1. **症状**：`Player-prev.log` 末尾 `archive:/CAB-651892cf…/… is corrupted! [Position out of bounds!]`，面包屑显示崩溃发生在 PlayerReport 面板打开瞬间。
2. **产物解剖**（UnityPy 提取游戏内 bundle 对比）：Builder 把该资产整体重编译——元素 ID 全部重排、references 膨胀 6.6×、丢失 `ScoutedProsAndCons` template using，**新增的 6 个元素被编译器整个丢弃**（连大小写不敏感匹配都为 0），且 bundle 重打包损坏。
3. **更深一层**：稳定运行多年的旧构建里该资产一直是"空壳"形态（8 元素 + 5 模板实例）——`panels/PlayerAttributesLargeBlock.uxml`（45 元素）在用户的 Builder 版本下**从未被成功应用过**；本次编辑触发重编译才暴露编译器缺陷。属性界面此前实际是原版结构 + CTRL 的 USS 样式。
4. **连带损伤**：Builder 的 `backups/originals/ui-tiles_assets_all.bundle` 在构建时被覆盖为损坏构建，恢复只能走 Steam 校验文件完整性。

**教训**：panels/ UXML 路线对该资产不可用（至少当前 Builder 版本如此）；结构性新增元素一律走 `_uabea` 补丁管道（与仓库其他补丁一致）。

### 第二次迭代：v1/v2 补丁无声无效——Builder 根本不应用 `_uabea`

15:45 与 16:01 两次构建均来自本仓库、补丁文件在位，但资产里毫无补丁痕迹。最终实锤两条：

1. **Builder 0.7.0 不支持 `_uabea` 补丁**：后端二进制（PyInstaller）中无 `_uabea`/`patch.json` 相关代码；同为 ui-tiles JSON 转储补丁的 `match-dugout_tile`（第 7 条 USS 规则）在游戏里也从未生效。README 的"必须在 UABEA 手工做"是字面事实。
2. 期间还修掉一个自有的 dump 格式 bug（元素内数组未包 `{"Array":...}`、`rid=-2` 缺 `data` 键）——虽然根因不在这，但格式规范本身值得记录。

### 第三次迭代（v3，最终方案）：UnityPy 直写游戏 bundle

绕过 Builder，用工程化工具 [fm26-skin-tool](https://github.com/SilasFan/fm-skin-tool)（本地 `F:\tools\fm26-skin-tool`；`python apply.py`，幂等）直接修补游戏目录的 `ui-tiles_assets_all.bundle`：动态定位信息列锚点 → 注入两个同级条目列（CA/PA，匹配 16:01 编译的"平铺列"结构习惯，克隆源取自本地元素）→ 全对象自检 → 带时间戳备份 → 原位部署。**部署验证通过，玩家已确认游戏中显示 CA/PA 数值**。

两个 UnityPy 技术注记：writer 对空类型托管引用（`rid=-2`）缺少 reader 的跳过逻辑，需猴子补丁对称修复；`rid=-2` 条目写回时补 `"data"` 键。**运维要点：每次 Builder Build + Apply 会覆盖该 bundle，之后运行 [fm26-skin-tool](https://github.com/SilasFan/fm-skin-tool) 的 `python apply.py`**（已打补丁时自动跳过）；`panels/PlayerAttributesLargeBlock.uxml` 保持存在（Builder 靠它产出完整布局）。
